## 1. 先分清楚各个程序的工作

厂家程序负责让电脑读到编码器、IMU 和雷达，并把速度指令发给下位机。
EGO-Planner 负责根据障碍物和目标位置规划轨迹，MPC 根据当前位置计算速度。
两者通过 ROS 话题与 TF 连接，不需要把厂家串口驱动改写成规划器。

```text
V550 编码器 + IMU → 厂家 EKF → /odom_combined ───→ EGO-Planner + MPC
                                                  ↑           ↓
二维雷达 /scan → 坐标变换 → /ego/obstacles → 局部地图       /ego/cmd_vel_raw
三维雷达 → Patchwork → 非地面点 → 坐标变换 ────┘                ↓
                                                       cmd_vel_guard
RViz /goal_pose → 目标坐标变换 → /ego/goal                     ↓
                                                         /cmd_vel
                                                            ↓
                                                     厂家驱动 → 下位机
```

二维、三维是两条可选输入链，不需要同时启用。
**只有单线二维雷达时，不运行地面分割**：扫描线主要描述一个高度上的障碍物，不能把它当成包含完整地面的三维点云。

厂家源码中可以确认：

| 项目 | 源码中的设置 | 部署时怎么处理 |
| --- | --- | --- |
| 底盘启动 | `turn_on_wheeltec_robot.launch.py` | 启动底盘、EKF、机器人 TF；它不启动雷达 |
| 默认车型 | 迁入配置已设为 `V550_mec`，原厂家默认是 `mini_mec` | 当前麦轮使用 `V550_mec`，其他车型需明确选择 |
| 底盘速度输入 | `/cmd_vel`，`geometry_msgs/msg/Twist` | EGO 输出经过实车看门狗后接入 |
| 原始编码器里程计 | `/odom` | 优先使用 EKF 融合结果而非它 |
| 融合里程计 | `/odom_combined` | 规划器、MPC、看门狗共用 |
| 里程计父/子坐标系 | `odom_combined` / `base_footprint` | 以实车 `echo` 结果复核 |
| 默认二维雷达 | 迁入配置已设为 `ls_N10Plus_uart`，`/scan`，`laser` | 按你确认的 N10p 串口版准备，安装与扫描结果需上车核对 |

## 2. 本次麦轮底盘采用什么运动方式

麦克纳姆轮在硬件上可以前后、横向和旋转运动，但当前工程的 MPC 控制输入只有前进速度 `v` 和偏航角速度 `w`。
本次先沿用这个模型，让麦轮车通过前后运动和转向跟踪轨迹，**不主动横移**；它并没有被改成四轮差速车型。
专用入口向厂家底盘和 TF 描述传入的车型始终是 `V550_mec`。

| `/cmd_vel` 分量 | 本次输出 |
| --- | --- |
| `linear.x` | 前后速度，初次调试限制绝对值为 0.15 m/s |
| `linear.y` | 恒为 0，不使用横移 |
| `angular.z` | 偏航角速度，初次调试限制绝对值为 0.4 rad/s |

以后如果要让车保持朝向并横移绕障，需要把 MPC 状态/输入、速度约束和轨迹跟踪方式一起扩展为全向模型。
直接放开 `linear.y` 或把车体速度当世界速度，不能完成这个改造。

通用入口还保留其他车型的选择，区别如下：

| 实际车型 | 本次接入范围 |
| --- | --- |
| `V550_4wd`，四轮差速/滑移转向 | 使用现有前进速度 + 偏航角速度 MPC；需要实测里程计与转向效果 |
| `V550_mec`，麦克纳姆轮 | 使用前进 + 转向，不使用横移，输出 `linear.y=0` |
| `V550_akm`，阿克曼前轮转向 | 可观察传感器和规划；**当前禁止启用实车行驶** |

阿克曼车不能原地转向，而现有 FSM 包含原地调头，轨迹优化器也没有最小转弯半径约束。
因此阿克曼不是只改一个话题就能执行：需要继续改搜索/轨迹曲率约束、起步调头逻辑，以及与实际转角接口匹配的控制模型。
启动文件会拒绝 `car_mode:=V550_akm drive:=true`，避免误把差速控制当成汽车转向控制。

后续二维雷达命令均按你已确认的 `V550_mec` 准备，无需再选择车型和传感器模式。

终端 C 检查：


## 6. 先只看规划效果

已启动厂家驱动的情况下：

```bash
ros2 launch ego_wheeltec v550_mec_2d.launch.py
```

本次首测应显式选择只前进配置：

```bash
ros2 launch ego_wheeltec v550_mec_2d.launch.py \
  planner_config:=$HOME/ego_ground_ws/src/ego-planner-for-ground-robot/ego_wheeltec/config/ego_v550_forward_only.yaml
```

这个命令默认 `drive:=false`，速度只发布到 `/ego/cmd_vel_checked`，不连接底盘的 `/cmd_vel`。
RViz 的 Fixed Frame 默认 `odom_combined`，使用 **2D Goal Pose** 工具在车前约 1 米的可见空地设置目标。

应检查：

- `/ego/obstacles`：墙壁和箱子位置应与现场一致，移动车辆时静止障碍物不应跟车移动。
- `/map_2d`：障碍物周围有膨胀区域，机器人当前位置不应被自身点云占据。
- `global_list`、`optimal_list`：当前实车 RViz 使用的是全局参考和 B 样条控制点折线；
  控制点折线不是实际采样后的平滑轨迹。仿真的绿色曲线/橙色实际路径显示节点尚未加入实车 launch。
- `/ego/cmd_vel_raw`：有规划/控制输出；默认保护器仍锁定，因此 checked 命令为零。

如需在这个隔离输出模式下观察看门狗转发，输入就绪后调用一次 enable，再重新发送目标即可；输出仍只在 checked 话题上。
若想由一个命令同时启动厂家底盘和雷达，可以在没有重复驱动的前提下加：

```bash
ros2 launch ego_wheeltec v550_mec_2d.launch.py \
  start_base:=true start_lidar:=true
```

这不会修改厂家源码中的车型默认值；当前启动选择通过 launch 参数传给底盘和 TF 描述。

## 7. 以后换成三维雷达时（你当前跳过这一节）

你当前只有单线二维雷达，运行上面的专用入口即可，**不会启动 Patchwork，也不需要填写地面分割参数**。
下面仅保留将来更换三维雷达的接入方法，不是本次必做步骤。

三维模式先运行已有的实际雷达驱动。必须获得 `sensor_msgs/msg/PointCloud2`、正确时间戳，以及传感器到 `base_footprint` 的实际外参。
如果驱动输出 Livox 自定义消息，先配置它输出标准 PointCloud2，不能把自定义消息直接接到此入口。

以下 `cloud_topic`、`lidar_frame`、`sensor_height` 和 `robot_height` 都是示例，需要替换：

```bash
ros2 launch ego_wheeltec v550_ego.launch.py \
  car_mode:=V550_mec sensor_mode:=cloud \
  cloud_topic:=/points_raw lidar_frame:=lidar_link sensor_height:=0.45 \
  robot_height:=0.65
```

`sensor_height` 指雷达测量原点距离地面的实际高度，单位米。
`robot_height` 指整车包含雷达、电脑、载荷等最高部件的离地高度。三维模式必须填写这两个实际测量值。
地面分割之后，天花板仍属于“非地面”，但不一定会碰到小车。
因此接口只保留车体坐标系中高度不超过 `robot_height + height_margin` 的障碍点；默认额外留出 0.10 米竖直余量。
否则把整个天花板投影到平面，会把本来可通行的地面误判为障碍。
这套高度裁剪按平整地面准备；坡道、台阶或车身明显倾斜时，需要另做地形与车体碰撞建模。
Patchwork 在雷达坐标系中工作，因此该坐标系需要 Z 轴向上；倾斜安装需要先做好外参/水平化处理。
实车入口让 Patchwork 在该传感器坐标系输出，再由 `sensor_bridge` 根据点云测量时间变换到里程计坐标。
接口会等待最多 0.15 秒让 EKF 的对应时刻 TF 到达；仍然缺失则丢弃该帧，不用最新 TF 代替历史测量。
观察 `/ego/ground` 是否主要是地面，`/ego/non_ground` 是否保留墙壁与箱子，最后 `/ego/obstacles` 是否位于正确的里程计坐标中。
稀疏度、种子高度阈值等在 `ego_wheeltec/config/ground_segmentation.yaml` 调整，不能把仿真参数当作已完成实车标定。

只读检查三维输入：

```bash
ros2 run ego_wheeltec preflight.py \
  --sensor-type cloud --sensor-topic /points_raw
```

## 8. 再进行低速实车测试

先核实急停可用；检查下位机在上位机进程死亡/通信中断时是否有超时停车。
本次软件测试能验证看门狗输出零速，但看门狗进程本身死亡后的物理停车，必须由下位机兜底并在实车确认。
首测选择平整、开阔、有人看护的室内区域，先做架空轮子的控制检查，再落地短距离测试。

关闭第 6 步的观察启动，在真实车辆终端启动：

```bash
ros2 launch ego_wheeltec v550_mec_2d.launch.py drive:=true
```

保持与观察阶段相同的首测配置：

```bash
ros2 launch ego_wheeltec v550_mec_2d.launch.py drive:=true \
  planner_config:=$HOME/ego_ground_ws/src/ego-planner-for-ground-robot/ego_wheeltec/config/ego_v550_forward_only.yaml
```

三维雷达则保留第 7 步的三维参数，再加 `drive:=true`。
默认限制前后速度绝对值不超过 **0.15 m/s**，偏航角速度绝对值不超过 **0.4 rad/s**。
上面的新首测配置把规划和 MPC 线速度进一步限制到 **0.10 m/s**，并要求只向前。
这是初次调试值，需要结合实际负载、抓地力和刹停距离确认。

检查命令发布者：

```bash
ros2 topic info /cmd_vel -v
ros2 topic echo /ego/guard_state
```

`/cmd_vel` 应只有 `ego_cmd_vel_guard` 一个发布者。看完持续状态输出后退出，再执行：

```bash
ros2 service call /ego/set_enabled std_srvs/srv/SetBool '{data: true}'
```

成功返回后，**重新发送一个约 1 米的近目标**。启动前、锁定时或上一次使能前发送的目标不会自动触发保护器转发。
看门狗在里程计、处理后的障碍物云、规划地图断流，或命令超时/无效时输出零速并解除使能。
数据恢复后不会自动恢复行驶，需要再次使能并重新发目标。

结束前先禁用：

```bash
ros2 service call /ego/set_enabled std_srvs/srv/SetBool '{data: false}'
```

确认车辆停住，再退出程序。现场急停优先于任何 ROS 命令。

## 9. 参数为什么必须重新确认

| 参数/接口 | 位置 | 原因 |
| --- | --- | --- |
| `car_mode` | 通用实车入口参数；专用入口固定为 `V550_mec` | 厂家底盘和 TF 必须使用真实车型 |
| `sensor_mode` | 通用实车入口参数；专用入口固定为 `scan` | 你的单线雷达不运行地面分割 |
| `sensor_height`、`lidar_frame` | 三维 launch 参数 | 影响地面种子选择及分割坐标 |
| `robot_height`、`height_margin` | 三维 launch 参数 | 按整车实际高度保留可能碰撞的点，排除足够高的天花板 |
| `planning_frame`、`base_frame` | 实车 launch 参数 | 必须和输入里程计的父/子 frame 一致 |
| `obstacles_inflation` | `ego_v550.yaml` | 至少覆盖实际车体半径、定位误差和所需余量；0.30 米是待实测的首测值 |
| `self_filter_radius` | 实车 launch 参数 | 默认不裁剪；如有自身反射，按真实车体设置，不能随意加大造成盲区 |
| 速度、加速度 | `ego_v550.yaml` | 规划器、优化器、B 样条、MPC 限值应协调 |
| `max_linear`、`max_angular` | `cmd_vel_guard.cpp` 默认参数 | 末端硬限制；调整 YAML 不会自动提高保护器限速 |
| `odom_twist_in_body_frame` | 两个规划/控制节点参数 | 厂家标准 Odometry 的速度在车体系，要旋转到位置所在的坐标系 |

标准 Odometry 的 pose 属于 `header.frame_id`，twist 属于 `child_frame_id`，见
[ROS 2 消息定义](https://github.com/ros2/common_interfaces/blob/humble/nav_msgs/msg/Odometry.msg)。
因此车朝正 Y 开时，车体 `vx=0.1` 对规划器应变为世界 `vy=0.1`，不能原样当成世界 `vx`。

## 10. 常见问题与当前范围

| 现象 | 优先检查 |
| --- | --- |
| 找不到 `ego_wheeltec` | 车上是否复制了本次新增源码、重新编译并 source |
| 有底盘没有雷达 | 厂家底盘 launch 不启动雷达，需要另外启动 |
| EGO 没有地图 | `/ego/obstacles` 的数据/TF/时间戳，及 `/benchmark/N` 是否被 remap |
| 障碍物跟着车走 | 是否真正做了 TF 变换，外参和测量时间是否正确 |
| 有轨迹但车不动 | `drive` 模式、enable 返回值、是否在使能后发送新目标、`guard_state` |
| 一使能就退出使能 | 检查里程计、障碍物云、`/map_2d` 的时间戳和频率 |
| 原地反复调头 | 车型是否正确、偏航方向和 odom 速度是否正确；阿克曼禁止直接行驶 |
| 小车始终被判在障碍里 | 自身反射、地面是否被当成障碍、膨胀是否大于可用空间 |
| 走远后定位漂移 | EKF 编码器 + IMU 不是全局定位，需要继续接入可靠 SLAM/定位 |

当前版本是局部规划首测方案：未知区域按空闲处理；地图的已占据格子没有完善的动态清除机制。
单线雷达也不能完整看到扫描平面以外的悬空物、低障碍和落差。
因此先验证可见区域内的短距离目标，不把本次接口接通等同于完成长期无人值守导航。
`odom_combined` 的累计位置还需保持在有限地图范围内；默认地图 X/Y 是以原点为中心的 ±20 米。
长期、多房间任务需要继续处理全局定位、全局路径、地图更新与更完整的碰撞检测。

## 12. 本次具体改了什么

| 文件/模块 | 本次改动 | 为什么实车需要 |
| --- | --- | --- |
| `ego_wheeltec/launch/v550_mec_2d.launch.py` | 固定本次麦轮车型与二维扫描输入，保留观察/执行及驱动启动选项 | 上车时不再手工选择车型和传感器模式 |
| `ego_wheeltec/launch/v550_ego.launch.py` | 新增实车入口，区分二维/三维传感器，接入厂家里程计与速度接口 | 替换仿真车辆和仿真时钟，不再依赖 Gazebo |
| `ego_wheeltec/src/sensor_bridge.cpp` | 真正变换点坐标与目标坐标，按车体高度和距离过滤 | 雷达坐标不等于里程计坐标，不能只修改 frame 名称 |
| `ego_wheeltec/src/cmd_vel_guard.cpp` | 启动锁定、限速、断流停车、重新使能后要求新目标 | 让仿真中的速度输出经过明确的实车执行入口 |
| `ego_wheeltec/scripts/preflight.py` | 只读检查输入、时间戳、频率和 TF | 在连接控制前先查清接口是否就绪 |
| `ego_replan_fsm.cpp`、`traj_server.cpp` | 增加可选的车体系速度到规划系速度旋转，实车入口开启 | 厂家标准 Odometry 的速度坐标与位置坐标不同 |
| `ego_replan_fsm.cpp`、`traj_server.cpp` | 状态切换时同步调头标志，MPC 在原地调头期间让出速度发布 | 避免旧轨迹的跟踪命令覆盖状态机的转向命令 |
| `grid_map.cpp` | 高度投影用米比较；二维地图使用配置的 frame 和有效原点四元数 | 避免将格子编号当高度，或在 RViz 中显示到错误坐标系 |
| `planning_visualization.cpp` | 轨迹标记统一使用配置的规划坐标系 | 实车默认在 `odom_combined` 中显示 |
| Patchwork `offline_own_data.cpp` | 增加 `allow_latest_tf` 参数；实车关闭最新 TF 回退，并用独立 TF 接收线程 | 防止测量时间与变换时间不一致；已有仿真保留原有回退默认值 |

没有修改你工作空间外的厂家串口驱动，也没有替你改写真实雷达安装外参。
这两项分别由厂家现有驱动和你的实际测量结果提供。
